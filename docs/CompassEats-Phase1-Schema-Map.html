Phase 1 Schema Map

Version 1.7 Written August 11, 2026 Status Signed off Aug 13 — in execution Companion to Re-Architecture Plan v1.14 §4

What happens to every piece of current data, in plain language. Part 1 gives a verdict for each of the 24 columns on the raw venues tab, using the measured fill counts from the Aug 11 column probe. Part 2 walks the new tables at review depth. Part 3 records the measured answers to what were open calls, and the one confirmation line that remains before the Supabase build starts.

01The 24 columns — verdict by verdict

ColumnVerdictWhat happens, and why
idTransform10,911 of 10,912 are Google placeIds used as the public key. Every venue gets a fresh internal ID (ve_ + random, minted once, never derived from the name). The placeId value moves to photo_refs — the one quarantine table allowed to hold a Google value — except rows the wrong-placeId triage marks bad, whose placeId is dropped, never re-looked-up.
slugMigrateBecomes a row in the slugs table (property = eats), keyed to the venue ID. Zero real URL collisions measured, so every current URL imports unchanged with no disambiguation.
nameMigrateInto venues.name, rename-protected by trigger. The 322-candidate contamination screen runs as a Phase 1 batch before names freeze.
city_slugTransformBecomes a foreign key to the cities table. A venue can no longer point at a city that does not exist — the wrong-city class gets a structural wall.
city_displayMigrate — with the winner ruleCity-level data, stored once per city in cities, not repeated per venue. The collapse is lossy without a rule, and the loss is measured (D/E, verified): 13 slugs carry conflicting display values — 460 venues, 22 minority rows — resolved by four cases: majority wins; casing normalised (kyoto/Kyoto); accent and alias variants written to cities.aliases (São Paulo, München, Wien); and the two live wrong labels corrected rather than carried — two Mexico City venues showing "Álvaro Obregón" and one George Town venue showing "Penang" today. One mechanism explains all of it: the same cityDisplay_() branch that preserves raw labels as neighborhood when a slug has a display entry writes them as the display when it lacks one — 110 hand-maintained entries against 3,167 cities — which is exactly why both columns’ raw strings route to city_label_source.
countryDerive — superseded (Response F)Venue-level country is never read by the migration. A city has exactly one country, and 45 slugs holding conflicting values (measured Aug 11: USA/United States, UK/United Kingdom, China vs Hong Kong, China) prove the venue row was always the wrong home. cities.country plus ISO derives once per city from the open geo resolution — Overture and Geoapify both return a country, and geo_city_cache already exists. One change closes four problems: the eight confirmed address-fragment rows, ~90 abbreviation variants, the wrong-country rows, and it turns Hong Kong / Macau / Taiwan / Puerto Rico into one written policy per city instead of whichever award tab loaded last. Any award-tab country string that disagrees with the resolved value is kept in city_label_source as a data-quality signal. Precondition (D/E request 42): the ~13 cross-country rows triage before venue-level country stops being read, since the conflicting string is the only automated signal for the cases that matter — outcomes are label fixed, venue moved, slug split, or per-city policy, and san-jose measured as a real split: San Jose, California and San José, Costa Rica share one slug today, so the derived country would silently misfile two venues and their centroid fallback with them.
neighborhoodMigrate — measuredAnswered by the Aug 11 provenance probe, not attestation: 302 rows, 82 distinct values, zero Google-vocabulary tokens. The values are award-source locality strings — all sixteen sampled values are CITY_ALIASES_ keys — the column is the award publisher’s own city string, preserved by cityDisplay_() at the moment the alias map folded it. Per Addendum A it migrates renamed, as city_label_source on the award/ingest row where provenance already lives — not as a venue neighbourhood, because a subset are separate towns (El Puerto de Santa María, Lasarte-Oria, Courchevel 1850) and roughly 300 venues would otherwise show a nearby town under a neighbourhood heading. City-variant values also feed the alias table. Now also definitive from source: Reshape.gs derives this column itself — when a raw award-source city label differs from the canonical city, the raw label is preserved here — and the enrichment script never references it. Alias machinery by construction, which is exactly how it migrates.
typeMigrateInto venues.category (restaurant / bar). Dual-category resolution already ran upstream.
lat · lngDrop — GoogleThe reason this migration exists. The new geo table fills only through the measured gates and channels, with google an impossible source value. Legacy values stay in the Sheet until the Phase 5 verified purge.
addressDrop — GoogleSame regime. The addresses table refills through the cascade: venue website, open data, gated guide capture — provenance on every row.
phoneDrop — empty0 rows. A stub that was never filled. If phone numbers ever matter, they arrive through the venue-website channel with provenance.
websiteDrop — empty0 rows. Also good news twice over: no stored Google website data exists, and the D11 channel keeps its search-and-verify discovery design — there never was a seed list.
reservation_urlDrop — empty0 rows. When reservation links arrive on the roadmap they are plain non-affiliate URLs in a new, provenance-carrying column, per the non-commercial constraint.
hours_jsonDrop — empty0 rows. Vestigial. Tonight mode's constraint is exactly as assumed: hours.days_open starts empty and fills at ingest with provenance and confidence.
price_tierSplit — measuredReversed from blanket drop by Addendum B, and verified in full: Google’s price_level is only ever a bare integer 1–4; the guides only ever publish currency symbols. The published column measures 7,095 symbol-shaped values, zero integers, zero other — every value is award-sourced and migrates with publisher provenance into the price table, joining source_exposure. The 2,244 Google integers sit only in the quarantined enrichment tab, unpublished, and are the precise D5 purge target. Future price still arrives only through ingest capture and menu-derived venue-website tiers.
cuisine_tagsMigrate — measuredAnswered by the probe: 8,637 rows (79.2%), 481 distinct values, and the vocabulary is unmistakably Michelin's editorial register — "Modern Cuisine," "Creative," "Country cooking," "Small eats." Three independent token tests agree: the review audit found zero Google-vocabulary tokens (conclusive and ambiguous both none, 479 distinct tokens), the published-data check found zero, and p1a4’s raw run printed two — traced to its double-space split rule, not the data (its 481 counted distinct values against the audit’s 479 distinct tokens: different units, same column). Zero is the number. Consequence, designed in: cuisine is guide-obtained data, so it migrates with legacy_guide provenance and joins the source_exposure view — a field-level publisher concentration that is now tracked, not assumed. Definitive from source: Reshape.gs maps the award-tab cuisine column straight into cuisine_tags; the enrichment script contains no reference to it.
blurb_short · blurb_longTransformOnly the 141 Option B records migrate, into the blurbs table keyed by venue ID and flagged for rewrite. The ~10,000 generated blurbs do not migrate, per the confirmed decision. The 141 is measured, per the Aug 11 review: importOptionB.gs (regenerated 2026-07-18, the runbook's sole source of truth) holds exactly 141 records — 131 restaurants + 10 bars. The CSV's 29 "have" rows are the documented-stale column and were never the basis.
chefMigrate137 rows, and the provenance is now exact: importOptionB.gs writes chef beside the blurbs — 141 records, 137 with a chef value. Hand-authored Option B data, the cleanest provenance in the file. Carries into venues.chef. Feeds the crediting rules in the blurb runbook.
awards_jsonTransformThe crown jewels. Unpacked into awards rows — venue, source, year, rank, category, distinction, source URL — with referential integrity to award_sources. The extended-list convention is settled in Part 3: parent slug + rank for all, with the extended label rendered above rank 50.
photo_urlDrop — empty0 rows, measured Aug 11. The stored-Places-photo question closes with nothing to purge. Photos remain live-fetched by placeId through the Worker, plus open-licensed entries in photo_refs with credit and licence fields.
statusMigrateInto venues.status. The closed_venues tab logic folds into this one field with the audit log recording every change.
last_verifiedMigrateInto venues.last_verified. Cheap, honest freshness metadata.

Net effect: fourteen columns migrate or transform, one is superseded by per-city derivation (country), three drop as Google-derived (lat, lng, address — the point of the exercise), five drop as empty stubs, and one placeId column splits between quarantine and the drop rule — fourteen plus one plus three plus five plus one covers all twenty-four. Zero calls remain open on columns. Standing rule from this review cycle: no column drops on attested or assumed provenance — every drop verdict cites a measurement. Three drop-defaults were reversed under it, preserving 302 + 8,637 + 7,095 = 16,034 award-sourced values.

02The new tables, in plain words

TablePlain-language contents
venuesOne row per venue: new internal ID, name (rename-protected), category, city link, status, chef, GERS ID where matched, last-verified date, and the stored norm_key that powers duplicate gating.
cities · regionsOne row per city with slug, display name, country + ISO code, region link, and aliases — the 200-plus-row hand-verified alias map imported as rows under a uniqueness constraint plus a reachability test (every alias must survive the normaliser), retiring its two measured source defects: the duplicated key block and apostrophe-form keys that can never fire. Cities also gain a kind flag — city or destination_region (Response F): the Aug 11 scan flagged 33 candidate labels, roughly eleven of which read as publisher destination regions (Cape Cod, The Berkshires, The Adirondacks, Orange County, Inland Empire, Willamette Valley, plus the five confirmed), covering 55 active venues in all. Brighton and Hove — one real city — proves the split needs the review surface, not a regex, so the 33 classify at Phase 1 before cities is written. Regional slugs are excluded from city-centroid geo fallback, and the frontend knows which kind it renders. The kind flag wins over venue reassignment by constraint, not preference: reassignment would change live /venue/$city/$slug paths, and existing URLs are unchanged by requirement. Country derives per city, never from venue rows (see the country verdict). Cities carry a venue count, and the migration dry run expects 52 venue-less cities (3,167 rows against 3,115 active slugs — closed-venue cities keeping their links), so an empty city is a query, not a discovery. Regions unchanged in concept from today's 111.
award_sourcesThe registry — 28 entries today — with attribution requirements, geo/price capability flags, the suspension switch, and the capture-permission switch per publisher.
awardsEvery award as its own row with source, year, rank, category, distinction, and source URL. An award cannot reference an unregistered source.
properties · listingsThe multi-property layer: CompassEats now, Compass Local in November, room for more. A listing joins a venue to a property with per-property fields like Local's trust tier.
slugs · redirectsEvery URL the site has ever answered, keyed to venue IDs, unique per property + city. Redirects cover any future slug change so no link ever dies.
geoCoordinates with precision tier (including venue_low), accept gate, source, source URL, publisher, capture date, confidence, agreement flag. google is an impossible source value by check constraint.
addressesRaw and structured address with native-script variant, same provenance fields, same no-Google constraint.
priceTier 1–4, source, method (published symbol or menu-derived), source URL, confidence. Same no-Google constraint. No confirmed source, no price shown.
hoursdays_open with provenance and confidence. Starts empty. Fills opportunistically at ingest.
blurbsShort and long text keyed by venue ID, method, version, status, and the fetched sources behind each fact. The 141 imports live here flagged for rewrite.
photo_refsThe single Google quarantine: placeId for the Worker. Open-licensed photos sit beside it with URL, credit, credit URL, and licence. Wrong placeIds were dropped before arrival.
ingest_batches · ingest_rowsThe staging ground for every future award-list import: raw rows, validation results, dedupe verdicts, approval record. Provenance is born here.
audit_logEvery row change, recorded by trigger: what, when, by which job or hand edit. Silent mutation becomes impossible by definition.
source_exposure (view)The live answer to "how much came from any one publisher," current and cumulative, checked against the D10 caps in every publish report.

03Sign-off — three calls and one confirmation

  1. Call #1 — neighborhood: CLOSED, measured keep. Zero Google vocabulary across 302 rows. Migrates with legacy_guide provenance; city-variant values route to the alias table.
  2. Call #2 — cuisine_tags: CLOSED, measured keep. Michelin's editorial vocabulary across 8,637 rows, no Google tokens in published values. Migrates with legacy_guide provenance and enters source_exposure tracking.
  3. Call #3 — extended-list convention: amended to all six slugs, and the dependency is in the change-set. Measured matrix: five -51-100 slugs sit in the frontend registry; europe-50-best-bars-51-100 lives only in the bar ingest array — the ingest-vs-registry drift, found one column over from where it was predicted. Three are populated (asia-restaurants 244, asia-bars 244, north-america-bars 99 = 587 award rows) and fold into parents with ranks 51–100; the rest retire empty. All six retire, everywhere they appear. Sequenced deliverables in the same change-set, before any next ingest: VALID_RESTAURANT_SLUGS, VALID_BAR_SLUGS, the Award Radar task prompt, the Watch List file — with the live Apps Script copies verified against the repo copies during the edit. Display rule, decided now: ranks above 50 render the extended-list label ("World's 50 Best Bars 51–100 — No. 63"), driven from award_sources, so Phase 4 inherits a rule instead of a surprise. Registry count, reconciled: frontend registry 28, ingest arrays 18 + 12 (james-beard shared, union 29), published data 24, and the handoff's 26 was a stale count. The canonical seed for award_sources is the reviewed union minus the six retirees, and every array, prompt, and watch list derives from that table afterwards — a slug can never again be valid at ingest and absent from display. Fold rule, hardened by measurement: all three populated extended slugs span ranks 51–100 — no restart-at-1 anywhere — but the Asia restaurants extended list was ingested twice: the parent slug already holds those rows for every year, and 243 of 244 are exact (venue, year, rank) duplicates living in published data today. The fold is therefore a dedupe-aware merge on (venue, source, year, rank), the awards table carries a uniqueness invariant on that key so a double ingest can never publish twice again, and the one non-exact pair routes to review. Fold safety cleared for all three (Addendum B, verified): asia-bars and north-america-bars fold clean with zero parent overlap; the asia-restaurants fold is a repair of a live defect — reshape dedupes awards on source-year-category, so the double-slugged rows both render today, about 244 award entries shown twice on live pages. The publish diff therefore shows ~244 award rows disappearing (22,091 → ~21,847), and the promote gate documentation says so in advance so repair never reads as loss. The 50 Best family carries four conventions, now all named; natively long lists (OAD, Top 500 Bars, 101 Steakhouses) sit outside the question entirely. The canonical seed is 23 — the measured union of every list (frontend registry 28, ingest arrays 29, Reshape’s BAR_SOURCES 9, published data 24; union 29) minus the six retirees. BAR_SOURCES is the fourth list, retired with reshape, with its own gap on record: europe-50-best-bars is absent from it today, latent behind force_type. The promote-gate advance notice carries both expected diffs: ~244 award rows and distinct slugs 24 → 21.
  4. Line 1 — RATIFIED, Aug 13. The map as amended is confirmed in full.
  5. Line 2 — ratify the placeId triage rule (per the Aug 11 review, it is a cost call and it is yours): each persisting collision group keeps the placeId only on its distance-verified pin_home_city row; every wrongly-pinned row drops its own. Cost: roughly 170–200 photos fall back to the compass mark. Alternatives on the table: group-wide drop (~371 photos) or a capped Places re-query (~$12, and it re-runs the exact mechanism that created the errors). Recommendation: the worklist rule. RATIFIED, Aug 13, with two conditions now part of the rule. One — the match is defined, conservatively: names match only if their normalised forms are equal, or one fully contains the other; anything else is a mismatch and drops. Ambiguity resolves toward dropping, because a wrong photo is worse than no photo. Two — the triage is dry-run gated: the preview run logs every group’s decision, kept venue name, and matched Google name; the live run executes only after Ben reviews that log. Every retained placeId’s recorded business name is read from existing tabs at zero API cost.

Both lines landed August 13. The Supabase build is underway — project setup first, then the schema, then the staged load with its verification report.

What this map already banked: zero URL collisions to resolve, zero stored Google photos, zero stored Google websites or phones, the duplicate rule settled at 15 groups / 30 rows, and a source that matches publish row for row. Phase 1 starts from the cleanest position this project has ever measured.
