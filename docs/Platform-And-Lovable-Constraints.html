01

GitHub ↔ Lovable Sync

Verified Jun 25 2026

How changes travel between GitHub and Lovable, and which direction controls what.

Direction & trigger

Bidirectional and automatic. Lovable edits push to GitHub automatically. GitHub commits (including web uploads) sync back into the Lovable sandbox via a GitHub App webhook — typically within seconds, at most ~1 minute. No manual "pull" button needed.

GitHub upload → live site path

Upload file on GitHub → commit lands on main → Lovable webhook fires → sandbox updates → Preview URL refreshes automatically → you verify → click Publish → production updates. Publishing is never automatic — it always requires a manual click.

Conflict risk — concurrent edits

Do not edit the same file in Lovable AND on GitHub at the same time. The sync is plain git, not conflict-aware. For large files like data/venues.json there is no useful 3-way merge — one side silently wins and the other's edit can be lost. Rule: GitHub is the sole writer for data/*.json. Never edit those files in Lovable chat while a GitHub upload is in flight.

Sync lag

Seconds to ~1 minute in normal operation. If a change hasn't appeared after 2 minutes, something is wrong (webhook miss, push to non-default branch) — not just slow.

Most reliable way to ship large data files (11 MB+)

GitHub web UI → repo → data/ folder → Add file → Upload files (drag-drop). Keep exact filename (venues.json, not venues (1).json) so it replaces rather than duplicates. Never use the GitHub text editor for files this size — it silently mishandles them and can commit an empty file. After upload: wait for sandbox to reflect the change, verify in Preview, then click Publish.

02

When Lovable Edits Files on Its Own

Verified Jun 25 2026

The most important section. Understand this before sending any prompt that touches data.

⚠ The incident — June 25, 2026

Lovable auto-resolved a load-time crash by setting awards to [] on every venue. This silenced the error but deleted all award data, breaking every guide page and award pill on the site. Root cause: the fix optimized for "make the red error go away" rather than "preserve the data." This is the canonical example of destructive default-to-empty behavior.

Does Lovable edit files between chat messages?

No. There is no background auto-healer. Lovable only edits files during a chat turn you started. Build failures, runtime errors, preview console errors — none of these cause file edits on their own. They only become edits if you send a message and Lovable acts on them.

What Lovable WILL edit within a turn (without being asked)

Fixing direct fallout from a change you asked for (e.g. you rename a symbol, Lovable updates import sites). If you ask to "fix the build" or "make the error go away," Lovable treats the whole error chain as in-scope. It should not edit unrelated files or "improve" code you didn't ask about — if it does, that's a mistake, not a feature.

The default-to-empty trap

When Lovable doesn't understand a data shape, it may default ambiguous fields to [] or null to make an error stop. This is destructive masking. The correct behavior is to stop and ask, or fail loudly — not silently empty data. Treat any Lovable "fix" that touches data-loading code with extreme suspicion.

Can you lock a file so Lovable never touches it?

No built-in lock flag exists. Three effective substitutes, in order of reliability:

1. Project memory (mem://): Add a rule like "Never modify src/lib/venues.ts without an explicit full-file replacement from the user. Defensive normalization here has wiped live data before." Always in context, treated as a hard rule.

2. Comment at top of file: // LOCKED — do not edit without explicit user instruction. Read every time Lovable opens the file.

3. Custom Knowledge (Project Settings → Customization → Knowledge): Same effect as a memory, surfaced on every turn.

Most reliable prompt wording to protect a specific file

Combine scope + file name + reason + what to do instead:

"Do not modify src/lib/venues.ts under any circumstance in this turn, even to fix a build or runtime error. If a fix appears to require editing it, stop and ask me first. This file is the source of truth for data normalization and has been broken by well-intentioned edits before."

The reason this works: it names the file explicitly AND tells Lovable what to do instead (stop and ask), which removes the "but the build is red" temptation.

Strongest possible read-only mode

Prefix any turn with: "Investigation only — do not change anything." Lovable will not write to disk at all under this header. This is the mechanism used for the Lovable Interview that produced this document.

Is there a UI toggle that disables all autonomous edits?

Not exactly. There is a Chat mode vs Build mode toggle in the Lovable UI. Chat mode limits Lovable to discussion only. Build mode (the default for this project) allows file edits. Switching to Chat mode for investigative sessions is an option, though the "Investigation only" prompt prefix achieves the same result within a turn.

Standing rule — locked in

When asking Lovable to rebuild after a data update, always include: "Do not modify src/lib/venues.ts or add any defensive award normalization — the data files are already correct."

03

Version History & Rollback

Verified Jun 25 2026

How to undo a bad change — to code and to the live site.

Does Lovable keep version history?

Yes. Every AI chat message that produces a code change creates a restorable checkpoint. Browse via the History tab at the top of chat (full list) or the Revert button under any AI message. History spans the project's full lifetime with no documented hard cap. Reverted points are archived, not destroyed — they can be reapplied.

Fastest rollback when the live site is broken

Two steps, both required: (1) Code: History tab → pick last known-good version → Revert. This rewrites the working tree and auto-pushes to GitHub. Preview rebuilds within seconds. (2) Live site: Reverting code does NOT automatically redeploy. You must then verify the preview looks correct, then click Publish to push the good state live. There is no one-click "rollback published deployment" button.

Is GitHub commit history a reliable rollback path?

Yes. A git revert <sha> pushed to main flows back into Lovable's sandbox within seconds. Same rule applies: it does not redeploy — you still click Publish after. Caveat: don't edit in Lovable AND GitHub simultaneously during a rollback or you'll get merge conflicts. Lovable's in-app History is faster for most cases; GitHub revert is better for surgical per-file rollbacks.

Preview vs published — safety model

Preview URL updates automatically on every code change. Published site (compasseats.com) only updates when you click Publish. This is the core safety gate — make changes, verify in Preview, then Publish only when satisfied. Exception: backend/edge-function changes deploy immediately on save; static pages and data files are gated behind Publish.

04

Build & Deploy Pipeline

Verified Jun 25 2026

What actually runs when Lovable builds and publishes this project.

Build commands (from package.json)

prebuild: bun run scripts/sync-sheet.ts
build: CI=true vite build
build:dev: vite build --mode development
Bun auto-runs prebuild before build. The sync script fires first, hits the missing-secrets guard, prints the SYNC SKIPPED banner, and exits cleanly. Then vite build runs with @cloudflare/vite-plugin and @tanstack/router-plugin.

The SYNC SKIPPED banner

Normal and expected on every build. scripts/sync-sheet.ts checks for SHEETS_API_KEY and COMPASSEATS_SHEET_ID at lines 328–341. On Pro plan these aren't available as Build Secrets, so the script throws SyncSkipped, which is caught and swallowed with a banner and process.exit(0). The build proceeds against the committed data/*.json. This is not a failure. Important caveat: DataValidationError (duplicate keys, schema failures) is not swallowed — it rethrows and kills the build.

Can the sync step be turned off entirely?

Yes — three changes required (describe only, don't make them unless intentional): remove "prebuild" script from package.json; delete the if (isBuild) { await runSync() } block in vite.config.ts; delete syncSheetPlugin() and its entry in the plugins array in vite.config.ts. The scripts/sync-sheet.ts file itself can stay for manual runs.

What "Publish" actually does

Takes the latest committed code on main → runs the full build pipeline → uploads the resulting Cloudflare Worker + static assets → points compasseats.lovable.app, compasseats.com, and www.compasseats.com at the new deployment. Every Publish is a fresh build from source. If the build fails, the previous deployment keeps serving — Publish does not blank the site on failure.

Hosting architecture

Lovable is the control plane; Cloudflare Workers is the runtime. The build emits a Cloudflare Workers bundle (SSR + static assets). Lovable's infrastructure deploys it to Cloudflare on Lovable's account. Custom domain config (compasseats.com) lives in Lovable's Project Settings → Domains — DNS A records point to 185.158.133.1 with a _lovable TXT verification record. SSL is auto-provisioned. There is no wrangler.toml in the repo.

File Size & Data File Limits

Verified Jun 25 2026

Where the ceilings are as venues.json grows.

LimitValueNotes
Chat upload to Lovable20 MB hard cap10 files max per message. venues.json at 11 MB fits; 25 MB would not.
GitHub web upload100 MB per fileThe reliable path for large data files. No resumability issues.
Cloudflare Worker bundle25 MB compressedApplies to the entire deployed artifact. JSON imported at module scope counts against this. Files in public/ served as static assets do not.
Editor displayTruncated above ~1 MBDisplay-only clipping. File on disk is intact. Do not use the Lovable editor to view or edit venues.json.
Practical breakpoints for venues.json

Up to ~15 MB: fine in current pipeline (loaded server-side at module scope).
20–25 MB: approaching chat upload cap; GitHub becomes the only ingest path. SSR cold-start parse time becomes noticeable.
25 MB+: Worker bundle pressure, slow preview rebuilds, sandbox memory issues. Consider splitting into per-city files or moving to runtime-fetched storage.

Best method ranking for replacing venues.json today

1st — GitHub web upload (drag-drop to data/ folder). Most reliable, 100 MB cap, syncs to Lovable automatically.
2nd — Chat upload to Lovable (attach file, Lovable copies to data/venues.json). Fine at 11 MB; fragile near 20 MB.
Never — Lovable code editor paste. Not designed for multi-MB JSON.

Special-treatment paths

No directories are special in the sync (/data, /public, /apps-script, /docs all sync like any other folder). The only truly special paths are: src/routeTree.gen.ts (auto-overwritten by TanStack Router on every build — never edit); .lovable/ (Lovable metadata — safe to read, don't hand-edit); .git/ (never copy in); node_modules/, dist/ (gitignored, don't sync).

07

What Lovable Can Do (That External Assistants Cannot)

Verified Jun 25 2026

Task routing: use Lovable for these, use Claude + GitHub for everything else.

Lovable's exclusive capabilities

Mutate the sandbox in place (edits land on main via sync without manual git). Trigger and inspect builds/deploys. Read published and preview Worker logs. Read/write runtime secrets. Manage workspace App Connectors and make authenticated calls through the connector gateway. Manage custom domain and publish settings. Invoke live server routes to test them (invoke-server-function). Browse the running app with a real Playwright Chromium browser (screenshots, console, network). Asset generation and CDN migration. Add/manage project memories (mem://) that persist across sessions.

Lovable's hard limitations

No rollback of a published deployment without revert + republish. Cannot manage Build Secrets (workspace-scoped, your account only). No scheduled jobs or cron primitives. Cannot be triggered headlessly — always requires a chat turn. Cannot edit registrar DNS for domains not purchased through Lovable. Cannot exceed 20 MB chat upload cap. Cannot write to the Worker filesystem at runtime. In-turn code editing behavior cannot be fully disabled — "Investigation only" prefix is the mechanism, not a hard lock.

Diagnostics Lovable can pull for you

Published Worker logs (last hour, up to 100 entries, keyword-filterable). Preview Worker logs (same). Browser console + network snapshot. Live HTTP probe of any route. Build-time error output from a sandbox build. Security and dependency scans on demand. What's not available: full historical build log per Publish (no per-publish artifact; details only visible while the build is running).

The Ideal Sheet → JSON → Live Workflow

Verified Jun 25 2026

The recommended path to get Sheet changes live with zero risk of code being auto-changed.

Today's workflow (manual, stable)

Edit Google Sheet → export .xlsx → Claude regenerates data/*.json → upload to GitHub via drag-drop → verify in Lovable Preview → click Publish. Works reliably today with no changes required.

Recommended future upgrade — GitHub Actions auto-sync:

1

One-time setup: Add SHEETS_API_KEY and COMPASSEATS_SHEET_ID to GitHub repo Secrets (Settings → Secrets and variables → Actions).

2

One-time setup: Add .github/workflows/sync-sheet.yml with a nightly cron trigger AND a manual "Run workflow" button. Steps: bun install → bun run scripts/sync-sheet.ts → commit changed data/*.json to main. Only data/ is touched — never src/.

3

Daily flow: Edit the Google Sheet → wait for nightly run, or click "Run workflow" in GitHub Actions for instant sync.

4

The Action commits updated JSON to main → syncs to Lovable sandbox in ~60s → Preview URL rebuilds automatically → verify it looks right.

5

Click Publish in Lovable. Live.

Three layers to lock in "no code edits"

1. Project memory: "Never modify files outside data/ in response to data-shaped problems. If a build fails because of data, surface the error — do not patch code to make it green."
2. Locked comment: // LOCKED — do not modify without explicit user approval at the top of src/lib/venues.ts and src/lib/schema.ts.
3. Turn prefix: "Investigation only — do not change anything." on any turn where you want read-only behavior.

Cloudflare Pages as an alternative (escape hatch)

Feasible: CF Pages free tier supports build-time env vars, so scripts/sync-sheet.ts would run automatically on every push. But: it removes the manual Publish gate (continuous deployment unless you use a separate production branch), requires a wrangler.toml, moves domain management to CF Pages, and narrows what Lovable can see and control. The GitHub Actions approach (above) achieves the Sheet auto-sync without any of these trade-offs. CF Pages is the right choice only if you also want continuous deployment and real per-build logs.
