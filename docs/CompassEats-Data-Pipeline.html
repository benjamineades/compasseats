Data Pipeline & Publish Reference

Version 2.0 Updated June 12, 2026 Owner Ben Status Proven live workflow

How data gets from the Google Sheet to the live site — and the workflow we actually use, now that the automatic build-time sync is confirmed unavailable on this plan. If a change is correct in the Sheet but wrong on the site, the answer is almost always "the JSON in the repo wasn't regenerated and re-committed." This doc is the ritual that prevents that.

v2.0 supersedes v1.0. v1.0 said the fix was to set Build Secrets. That fix is not available — Build Secrets are a Lovable Enterprise-only feature, and this project isn't on Enterprise. The build-time Sheet sync therefore cannot run on a normal publish; the SYNC SKIPPED banner is the permanent, expected state. The real workflow is manual JSON regeneration + GitHub commit, documented below.

01How data flows

The frontend never touches Google Sheets. Everything is baked into static JSON, which is prerendered into HTML at build time.

Google Sheet  (source of truth · ID 1dKJY_woXdbO…cI5s)
  ↓  Apps Script pipeline — reshape → mergeDuplicateVenues → blurbs → clearWrongCity → importOptionB → generateCitiesTab
  ↓  build-time sync (scripts/sync-sheet.ts) — SKIPS on our plan, see §02
  ↓  data/venues.json · data/cities.json · data/venues-index.json · data/sync-report.json
  ↓  prerender (TanStack Start, vite.config.ts) — every /city/… and /venue/… page → static HTML
  ↓  Cloudflare deploy — new HTML served immediately (no CDN purge needed)

The frontend reads the committed JSON via plain imports in src/lib/venues.ts (lines ~19–21). Pages are fully prerendered — the live site does not re-read data per request. So the deployed HTML is only ever as fresh as data/venues.json was at build time.

02Why the automatic sync can't run root cause

The build only re-fetches the Sheet if two variables exist in the build environment: SHEETS_API_KEY (or GOOGLE_SHEETS_API_KEY) and COMPASSEATS_SHEET_ID. On Lovable those are Build Secrets — an Enterprise-only feature. Runtime/Cloud secrets are not visible to the build. So runSync() throws SyncSkipped, the build swallows it with a warning, and ships whatever JSON is already committed:

⚠️  SYNC SKIPPED — using committed JSON, data may be stale

This banner appears on every publish and is normal. It does not mean the publish failed. It means: "I deployed the committed JSON as-is." The committed JSON is therefore the thing we maintain by hand.

This was the cause of months of "stale build" confusion. Belcanto's missing stars, Kadeau, Plénitude, wrong-city blurbs — all traced to the sync skipping since June 9, 2026, redeploying old JSON every publish. Correct Sheet data never reached the site because nothing regenerated the JSON.

03The publish workflow (what we actually do) proven live

Proven end-to-end on June 12, 2026 — Belcanto ★★, Kadeau ★★★, Sushi Sho ★★★ (NYC) + ★ (Stockholm) all went live through these steps.

1
Run the full Apps Script pipeline in order on the Sheet — reshape → mergeDuplicateVenues → importBlurbsFromDrive → clearWrongCityBlurbs → importOptionB → generateCitiesTab. The Sheet must be correct first.
2
Export the Sheet (File → Download → .xlsx) and hand it to Claude. Claude regenerates the four data files with a faithful reproduction of sync-sheet.ts — same rowToVenue/rowToCity/index logic, same schema validation, plus euro→dollar price normalization so non-dollar Michelin data passes. Claude returns: venues.json, cities.json, venues-index.json, sync-report.json.
3
Commit the four files via GitHub web. Repo → data folder → Add file → Upload files → drag all four in (same names = replace) → commit to main. Use upload, not the text editor — the editor chokes on the 11 MB venues.json and can present a misleading blank box.
4
Publish in Lovable. The build prints SYNC SKIPPED (expected) and deploys the freshly committed JSON.
5
Verify on the live site — see §04.

Two hazards to avoid. (1) Never paste into a GitHub editor that shows an empty "Enter file contents here" box for a file that should be huge — committing it would wipe that dataset. Cancel and use Upload instead. (2) Make sure filenames are exact (venues.json, not venues (1).json) or you create a duplicate instead of replacing.

04Post-publish verification (every time)

"I republished" is not the same as "the data refreshed." Confirm with your own eyes.

Check A — the data file actually changed

In the repo, the four files under data/ should show your recent commit time ("Add files via upload, X minutes ago"). If they show an old date, the upload didn't land.

Check B — a known value is present

Spot-check a venue you just changed, in the file the site reads:

jq '.[] | select(.slug=="belcanto") | .awards' data/venues.json

If the value you expect (e.g. a michelin award) isn't there, the page won't show it — regardless of what the Sheet says.

Check C — the live page

Load the actual page (e.g. the Lisbon city page) and confirm the change is visible. Because pages are prerendered, what you see is exactly the committed JSON.

Rule of thumb: live HTML is built from data/venues.json. Sheet-correct-but-site-wrong always means "the JSON wasn't regenerated and re-committed." Regenerate → upload → publish.

05What is NOT the problem

  • No CDN/edge cache to purge. Cloudflare serves new HTML as soon as the deploy is live.
  • No KV, R2, Supabase, or runtime data store between the JSON and the page.
  • Browser cache is the only client-side layer — a hard refresh rules it out.
  • The SYNC SKIPPED banner is expected, not an error. Don't chase it.
  • Scoring/display code is rarely the cause — if the award isn't in the committed JSON, no formula can show it. Check the data first.

06The escape hatch (if commits get tedious) future option

The manual upload works but is a chore on every data change. The clean long-term fix — without Lovable Enterprise — is to point Cloudflare Pages at the same GitHub repo with SHEETS_API_KEY and COMPASSEATS_SHEET_ID set as build env vars (Cloudflare's free tier supports build-time env vars — confirm current terms when the time comes). That makes the original build-time sync "just work" on every deploy, no manual JSON.

This is a roughly half-day change, not a migration: the repo is a standard TanStack Start app with no Lovable lock-in, so the data and frontend are already portable. Treat the manual workflow as the test — if it stays smooth, stay on Lovable; if it becomes friction, this is the move. Don't do it preemptively.
