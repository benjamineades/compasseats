01 — The Idea · N

A compass for the hungry & thirsty, anywhere on earth.

CompassEats lets anyone search a city and instantly see its best restaurants and cocktail bars, ranked from the guides that actually matter — Michelin, World's 50 Best, James Beard, the Spirited Awards, and more. No crowd noise. Just a clear line to the places worth your time.

The product exists to end the "where should we eat/drink?" argument — to be the well-traveled friend who always knows the spot.

Strategic positioning

  • Go deep, not wide. Restaurants + bars only. No hotels, wineries, or "experiences."
  • Cocktail bars are the wedge. Neither main competitor fully owns this space — it's our differentiator.
  • Stay simple. No accounts, no social feed, no points. Search → see the best → go.

The competitors

Our edge: authority-ranked, restaurant and bar, cross-guide in one view, map-first, dead simple.

The big architectural shift

CompassEats is migrating away from AI-generated venues (the old approach: venues invented by an LLM at request time — ephemeral, no permalinks, bad for SEO) to static data built from the Google Sheet. This is the single most important upgrade: it gives every venue a permanent, crawlable page — exactly the advantage competitors have and we didn't.

Page URLs (permalinks)

Page typeURL patternExample
City page/city/[slug]/city/tokyo
Venue page/venue/[city]/[slug]/venue/tokyo/sushi-saito
Award page/award/[slug]/award/worlds-50-best
Cities index/cities/cities — collapsible Continent → Country → City
Guides index/guides/guides — all award sources, global/regional

City page layout — stacked, collapsible eat/drink sections

As of June 14, 2026 the city page no longer interleaves restaurants and bars in one ranked list. The old single list cross-scored the two types against each other, so a mid-pack 50 Best bar could outrank a two-Michelin-star restaurant — a false comparison (the per-type scoring in getVenuePrestige was always correct; only the render mixed them). The page now shows two stacked sections: “Where to eat” then “Where to drink”, each ranked on its own prestige scale and never interleaved. A section with zero venues is omitted entirely.

Both sections are collapsible accordions, collapsed by default (Radix Collapsible from @/components/ui/collapsible), each header showing a count — “Where to drink 76”. This was a deliberate UX choice for the cocktail-bar wedge: a bar-seeker lands on the page and taps “drink” without scrolling past dozens of restaurants. The page-level heading is “What’s charted in {city}”; the existing All / Restaurants / Cocktail Bars toggle is unchanged and filters over the sections (selecting one type hides the other section). Per-section row cap is INITIAL_ROW_CAP = 10 with an independent “Show all” per section. All of this lives in src/routes/city.$slug.tsx; it is a frontend-only change — no JSON regeneration needed.

Design path not taken (recorded so it isn’t relitigated): side-by-side eat/drink columns were rejected — only ~22 cities have 5+ bars, and the median “both” city has just 2, so columns would render a tall restaurant list beside a near-empty bar column. Stacked collapsible sections scale cleanly from 2 bars to 76.

★ The golden rule

A venue becomes "charted" (visible on the site) only when it is in venues, has at least one accolade, and has its required fields filled (name, type, city, address, lat/lng). Missing any required field sends it to needs_enrichment instead, and it won't show until fixed.

04 — The Headline Workflow · SE

How to add venues.

Here's the full chain of what must be true for a new venue to appear as charted on the website.

1. Venue lands in the venues tab
2. It has at least one accolade — this makes it charted
3. Required fields filled — name, type, city, address, lat/lng
4. Its city exists in cities — so it maps to a city page
5. Build-time sync regenerates the static JSON
6. Site redeploys — venue is live and charted ✅

Path A — Add a whole award list (the normal way)

Use this when you have a published list (e.g. "Asia's 50 Best Bars 2025").

  1. Open the matching award tab (or create a new one — see §5 if the source is brand new).
  2. Paste the list in. For bars, use the bar-ingest tool: run makeBarImportTemplate, fill it, then run ingestBarLists (§6).
  3. Run reshape.gs. Merges new entries into venues and de-duplicates. Incomplete rows route to needs_enrichment.
  4. Enrich anything in needs_enrichment (§7) — fill addresses and coordinates.
  5. Re-run cities.gs if you added venues in a previously-uncharted city.
  6. Sync & deploy (§8 / §10).

Path B — Add a single venue by hand

For a one-off addition or quick fix (this is how the Sushi Ogawa proof-of-concept was done).

  1. Go to the venues tab and add a new row.
  2. Fill the core columns: name, type, city, country, address.
  3. Add coordinates (lat/lng). No coords yet? Leave blank and enrich later — but it won't go live without them.
  4. Add at least one accolade. No accolade = not charted.
  5. Make sure the city value exactly matches a row in cities. New city → re-run cities.gs.
  6. Sync & deploy.
🧠 Why the accolade matters

"Charted" literally means sheet-matched-with-an-accolade. A place with no award attached is just a location — CompassEats only shows venues an authority has vouched for.

05 — Awards · S

How to add a new accolade.

There are two layers (e.g. La Liste, Gault & Millau, Tabelog, OAD, Forbes). Both must be done for it to work end-to-end.

Layer 1 — In the Google Sheet (the data)

  1. Create a new tab named for the source (e.g. La Liste).
  2. Paste the list, matching the column shape of the other award tabs (name, city, rank/year).
  3. Run reshape.gs so its entries flow into venues. Reshape merges all award tabs, so a new one is picked up automatically as long as it follows the shape.

Layer 2 — In the code (the registry)

The site needs to know about the source to label it, give it an icon, weight it, and build its /award/[slug] page.

  1. Open src/lib/schema.ts.
  2. Find the AWARD_SOURCES registry (currently 18 sources).
  3. Add a new entry — display name, slug, weight/styling. Mirror the existing entries.
  4. Special card treatment goes here (e.g. OAD rank 200+ is deprioritized vs. Michelin / 50 Best).
  5. Commit. Next build picks it up.
⚙️ Do both layers

Layer 1 without Layer 2 → the data exists but the site won't render the source nicely. Layer 2 without Layer 1 → an empty award page.

★ Four verified normKey_ patches live in reshape

To match award rows to Places Enrichment, reshape normalizes venue names to a key. Four character-class fixes have been verified against Places and live in normKey_: strip apostrophes (so Tetsuya's → tetsuyas), convert & → "and" (so Jigger & Pony → jigger and pony), strip Unicode fractions (so 8½ → 8), and strip superscripts (so Tanière³ → taniere). Each was verified by checking the actual Places Enrichment.normalizedKey before patching. Don't add more without doing the same.

⚠️ The photos script bills per image load

Don't run photos.gs casually. The plan is to cache images to a CDN first, then point photo_url at the cached copies so we aren't paying per page view. Leave it parked until that caching step is in place.

◆ On cities.gs preserving edits

It's written so re-running won't wipe manual fields you've filled — like hero_image_url. Re-run safely to pick up new cities without losing hand-curated touches. (timezone is now dormant since "Open Today" was dropped — leave blank.)

07 — Data Quality · W

Enriching venues & filling gaps.

"Enrichment" = pairing an award-winning venue with the geo data (place ID, lat/lng, address) it needs to go live on the site. The whole pipeline hinges on reshape's matching step — so it's worth understanding what that step actually does.

How reshape's matching actually works

City slugs are alias-aware (June 12, 2026). Reshape builds city_slug via slugify_(cityKey_(v.city), …), so the CITY_ALIASES_ map controls the actual page slug, not just award-grouping identity. Adding an alias (e.g. 'new york city': 'new york') now merges those venues onto one city page automatically. This fixed the New York split (new-york-city → new-york, reuniting the three-stars) and the rio-de-janiero typo. generateCitiesTab rebuilds cities from venues, so emptied city rows self-prune.

Reshape doesn't compare award rows against the venues tab. It compares them against Places Enrichment — and the geo lookup is name-only, no city. For each award row:

  1. The venue name is normalized via normKey_ (lowercase, accents stripped, apostrophes removed, & → "and", fractions / superscripts stripped, then alphanumeric-only).
  2. That normalized key is looked up in Places Enrichment.normalizedKey to attach geo (placeId, lat/lng).
  3. The venue's identity is normKey(name) + '|' + cityKey(city) (as of June 5, 2026) — name and city. Two award rows merge into one venue only if they share both. This is what keeps same-name venues in different cities (Atlas Atlanta vs Atlas Singapore) as separate records.
  4. If no enrichment match is found, the venue is still created from its name+city identity and lands in needs_enrichment with no geo.
⚠ Geo is still name-only — the open follow-on

Identity is name+city, but the geo attached in step 2 is matched by name alone. So a venue split out by the identity fix can inherit the wrong city's coordinates (Atlas Singapore briefly carried Atlanta's geo). Punch-listed as "per-city geo matching" — make geoEnrich and reshape both key geo on name+city. Until then, the residual is duplicate rows / occasional wrong pins, not wrong awards.

★ What "unmatched" really means in reshape's log

The award rows unmatched count is not "couldn't be matched to a venue." It means "this award row's normalized name was not found in Places Enrichment." The venue still gets created — it just has no geo, so it goes to needs_enrichment. Every award row produces a venue somewhere; nothing is silently dropped.

The needs_enrichment tab — your real triage target

Reshape labels every row in needs_enrichment with a reason — one of three:

ReasonWhat it meansHow to fix
has placeId, missing coordsPlaces matched the name but lat/lng came back empty.Re-run Places enrichment for this placeId.
no placeIdName didn't match anything in Places Enrichment, but a city was provided by the award tab.Find the venue in Google Places, add a row to Places Enrichment with the correct normalizedKey.
no placeId + no cityNo Places match and no city. Worst case.Research the venue manually, then enrich.

The audit workflow

Don't work needs_enrichment top-to-bottom. Run enrichment-audit.gs first — it ranks every row by award prestige (a Michelin 3-Star is worth more attention than a single-list mention) and writes a triage-ready enrichment_audit tab.

  1. Run auditEnrichment from enrichment-audit.gs (see §6).
  2. Open the enrichment_audit tab. It's sorted by priority — row 1 is the highest-prestige venue still missing geo.
  3. Color hint: green = easiest (missing coords only), yellow = needs a Places lookup, red = no city either.
  4. Work top-down. For each row, the suggested_action column tells you the literal next step.
  5. After a batch of fixes, run reshape → run auditEnrichment again → watch the list shrink.

Automated geo-enrichment (geo-enrich.gs)

The audit tells you what to enrich; geo-enrich.gs does it automatically via the Google Places API instead of one venue at a time by hand. It reads enrichment_audit top-down (highest prestige first), looks each venue up by name + city, and writes the result to Places Enrichment — so the next reshape graduates it into venues.

Setup (one-time): store a Google Maps Platform key (with Places API (New) enabled, restricted to that API) in Project Settings → Script Properties as PLACES_API_KEY. The key never lives in the code.

The loop:

  1. Run geoEnrich. It processes up to MAX_TO_PROCESS venues per run (start small, e.g. 200, to verify match quality before spending). Resumable — re-run to continue; it skips anything already done.
  2. A safety gate auto-accepts only when the returned name and city both match; anything ambiguous is parked in enrichment_review. Permanently-closed venues route straight to closed_venues.
  3. Run suggestReviewDecisions — it pre-fills the review tab's decision column with ACCEPT? / REJECT? suggestions (strong name match vs. no shared words).
  4. Scan the suggestions. Most parked rows are correct venues that tripped on localized city spellings (Moskva/Moscow, München/Munich, 京都/Kyoto) — those are safe accepts. Watch for same-chain different-branch traps (e.g. a Miami restaurant matched to its Chicago sibling) and flip those to REJECT?. The address column is your tell.
  5. Run convertSuggestions (turns ? suggestions into final ACCEPT/REJECT), then acceptReviewRows (copies accepts into Places Enrichment, drops rejects).
  6. Run reshape → the accepted venues go live.

Cost. Places Text Search bills ~$32/1,000 lookups (often inside the monthly free credit, which resets on the 1st). One request per venue. The per-run cap is your spend control; there is no time-based cooldown — geoEnrich simply has nothing to do until a new ingest adds more un-geocoded venues to needs_enrichment.

Geoapify vs. Google. geocode.gs (Geoapify) fills lat/lng only and is free — but reshape's completeness test also requires a placeId, which only geo-enrich.gs (Google Places) supplies. Use Geoapify as a fallback for the long tail Google can't resolve, not as the primary enricher.

The closed_venues tab

Some venues are permanently closed (Charlie Trotter's, El Bulli, Le Gavroche post-Jan 2024). The brand's voice is "point you to the spot" — you can't go to a closed restaurant, so closed venues are excluded from the site.

To exclude one, add a row to the closed_venues tab with two columns:

namecity
Charlie Trotter'sChicago
Le GavrocheLondon

Reshape reads this tab on every run and excludes matching venues from both venues and needs_enrichment. The final log line closed excluded: N shows how many were filtered. Clear the tab to bring them back — fully reversible.

How to add a new normKey_ patch

If a high-prestige venue stays stuck in needs_enrichment and you suspect a normalization bug, follow this protocol — never skip it:

  1. Verify first. Open the Places Enrichment tab. ⌘F / Ctrl+F the normalizedKey column for the venue name. See exactly what key Places stores.
  2. Compare to what reshape's current normKey_ would produce. If they differ, you've found the gap.
  3. One regex change per patch. Don't bundle multiple character-class fixes into one save. Bundling makes regressions hard to attribute.
  4. Apply the patch → save → re-run reshape → re-run the audit.
  5. If the unmatched count goes up, revert immediately. (This has happened — assuming a pattern from one or two examples instead of verifying caused a 700-venue regression that had to be rolled back.)
✓ Fixed June 5, 2026 — the collision that was once a known limitation

This was punch-listed for months: reshape's identity was name-only, so same-named venues in different cities collapsed into one record (all L'Atelier de Joël Robuchon locations; Atlas Atlanta inheriting Atlas Singapore's bar awards and type). A collision_audit found 603 names appearing in 2+ cities. Fixed by adding a cityKey_ helper and changing identity to normKey(name) + '|' + cityKey(city). Result: venues 9,863 → 11,224, match rate held (unmatched stayed at 106). Atlas, Bacchanalia, Singapore all verified correct.

Two residuals it created, with a fixed fix-order: (1) geo is still matched by name, so split venues can carry a sibling's coordinates — punch-listed as per-city geo matching; (2) one real venue can split into multiple rows when sources spell its city differently (Lisboa/Lisbon, antwerp/anterwp) — punch-listed as city-label canonicalization. Order is mandatory: geo fix FIRST, then canonicalization. Building the canonicalization map before the geo fix fails — an attempt to auto-generate it from the contaminated audit data chained false matches and tried to merge 236 unrelated cities into "new-york." The dupe data isn't trustworthy until geo is per-city.

Outlier detection

A passive pass flags suspicious data (coords in the wrong country, a wildly off rank). The Sushi Ogawa fix was the proof-of-concept — spot the anomaly, correct it in the Sheet, re-sync.

10 — Shipping · NNE

Deploying the site.

The real publish workflow (corrected June 12, 2026). The build-time Sheet sync cannot run without Enterprise Build Secrets, so the sync has effectively never run on a normal publish. The working process is now: (1) run the Apps Script pipeline so the Sheet is correct; (2) export the Sheet and regenerate the four data files (data/venues.json, data/cities.json, data/venues-index.json, data/sync-report.json) — a faithful reproduction of sync-sheet.ts; (3) upload them via GitHub web → Add file → Upload files (drag-drop replace; the text editor chokes on the 11 MB venues.json); (4) Publish in Lovable. Verify: data/sync-report.json commit time is recent, and jq a known venue. See the dedicated Data Pipeline living doc (v2.0) for the full ritual. Escape hatch if manual commits get tedious: point Cloudflare Pages at the repo with the two env vars set (free-tier build env vars) — confirm terms when the time comes; the repo is standard TanStack Start, no lock-in.
⚠️ Known live-site issue

compasseats.com may still serve an older build even when the repo is correct — the domain needs republishing. After any change, confirm the live site actually updated.

The deploy chain

  1. Make your change (Sheet data, or code via Lovable).
  2. If data: run the relevant Apps Scripts (§6) so the venues and cities tabs regenerate.
  3. Click Publish in Lovable. Important (corrected June 12, 2026): the build's Sheet sync does not run on this plan — it requires SHEETS_API_KEY + COMPASSEATS_SHEET_ID as Build Secrets, which are Lovable Enterprise-only. Every publish prints ⚠️ SYNC SKIPPED — using committed JSON, data may be stale and redeploys whatever JSON is committed. That banner is expected, not an error.
  4. Verify it's live on compasseats.com — not just in Lovable's preview. Load the real URL in a fresh tab and hard-refresh.
⚠️ How the sync actually runs (hard-won, June 1)

Lovable's publish runs only the Vite build — it does not execute prebuild/postinstall or any other package.json lifecycle script. The Sheet sync is therefore wired in as a Vite plugin (syncSheetPlugin() in vite.config.ts, apply:"build", buildStart → runSync()). If you ever see stale data on a publish, the sync didn't run — check this plugin first.

What the sync needs to succeed

  • Build Secrets (Lovable → Workspace Settings → Build Secrets, not runtime secrets): SHEETS_API_KEY (a real Google API key, starts with AIza) and COMPASSEATS_SHEET_ID. Note: the connector-managed GOOGLE_SHEETS_API_KEY holds a Lovable token (lovc…), not a Google key, and is locked — that's why the code reads SHEETS_API_KEY first and only falls back to GOOGLE_SHEETS_API_KEY.
  • The Google key must have the Google Sheets API enabled in its Cloud project and be restricted to that API.
  • The Sheet must be link-shared "Anyone with the link → Viewer." An API key (no OAuth) can only read public Sheets; a restricted Sheet returns 403 PERMISSION_DENIED.

The validation gate

The sync splits failures two ways: a data-validation error (duplicate slugs, bad country_code, schema failures) throws DataValidationError and fails the build — by design, so bad data can't silently ship. A Sheet-unreachable error (missing secret, 403, network) throws SyncSkipped, prints a loud ⚠️ SYNC SKIPPED banner, and lets the build continue on the committed JSON. If a publish fails the build, read the error: it's almost always a data problem to fix in the Sheet.

Deploy troubleshooting — hard-won lessons

The June 4 2026 publish failed eight times before going green, on four stacked, distinct causes — each masked the next, and a misleading symptom (a recurring ReadableStream error) sent debugging down wrong paths for hours. If a publish fails mysteriously, check these before theorizing:

The ReadableStream red herring. An error dump showing body: { stream: ReadableStream { disturbed: false, state: 'readable' } } is not a streaming-SSR problem. It's the unconsumed body of a 500 response — the prerenderer throws before reading the body because the response wasn't OK. The real error is whatever produced the 500, which is often swallowed by brandedErrorResponse. First move: get the real exception surfaced (temporarily log it before it's converted to the branded 500, or reproduce via vite preview), don't chase the stream.

  1. Stale prerender data. vite.config.ts builds the prerender page list from the venue JSON. That list must be generated after the Sheet sync, or it's built from stale committed JSON. Fixed via sync-before-pages at config load + an idempotent memoized runSync() (one sync per process, called from both a top-level gate and the backup plugin). Tell-tale: prerender page count looks older/smaller than current venue count.
  2. Missing server entry. The TanStack preview/prerender server imports dist/server/server.js, but the Cloudflare plugin emits dist/server/index.mjs (its MAIN_ENTRY_NAME is hardcoded to index, and the preview plugin hardcodes a .js extension). The emitServerJsAlias shim must write a server.js that re-exports from index.mjs, and it must check for the right source filename (index.mjs, not index.js). Tell-tale: ERR_MODULE_NOT_FOUND: Cannot find module '…/dist/server/server.js'.
  3. augmentReq read-only ip. The Cloudflare adapter's augmentReq() assigns request.ip, but the preview/prerender HTTP path passes a spec Request whose ip is a read-only getter → TypeError: Cannot set property ip… thrown before SSR runs, producing the 500. Fixed in the emitServerJsAlias shim by wrapping the incoming request in a Proxy that stores writes (ip, cf, waitUntil, etc.) on a side overrides map instead of touching the read-only getter.
  4. Orphan city_slug 404s. Venues referencing a city_slug with no row in the cities tab cause the prerender link-crawler to hit /city/{slug}/ → 404 → hard build fail. Fixed by re-running cities.gs (it builds city rows from venue slugs) + a sync-time orphan validation that now fails loud at sync rather than deep in prerender. After enrichment adds venues in new cities, always re-run cities.gs, then check country codes (see below).

country_code blanks (recurring). cities.gs can't auto-map small territories to a 2-letter ISO code, leaving a blank that hard-fails schema validation. Hit twice on this deploy: Cayman → KY, Jersey → JE. After every cities.gs run, check with =FILTER(A:A, LEN(D:D)<>2) in an empty cell and hand-fill any blank (Maldives MV, Jamaica JM, Rwanda RW, etc.), then delete the formula.

The build:dev sync gap. The root cause of the stale-data issue: build has a prebuild sync hook but build:dev (Lovable's preview pipeline) does not, so preview builds skipped sync. The idempotent runSync() now covers both, but a prebuild:dev hook would make the two modes truly consistent (punch-list item).

Meta-lesson from this session: when a build keeps failing on slightly different routes with the same error, stop patching forward. Force a root-cause diagnosis — surface the real (un-branded) exception, and revert-and-observe (temporarily undo a suspected fix and see if the error changes). Stacking blind patches is how one bug becomes six. Several edits from this saga (router.tsx trailing-slash, start.ts/server.ts redirect-passthrough) were later proven inert and are flagged for cleanup.

12 — Definitions · True N

Glossary.

Terms specific to CompassEats and the tools it's built on.

Project terms

Charted
A venue in the venues tab and matched with at least one accolade — i.e. sheet-matched-with-an-accolade. Charted venues are the ones shown on the site.
Accolade / Award
A recognition from an authoritative guide attached to a venue (source + rank + year). Having one is what makes a venue charted.
Award source
The guide itself — Michelin, World's 50 Best, James Beard, Spirited Awards, OAD, etc.
The wedge
The strategic differentiator — cocktail bars, which competitors don't fully own.
venues tab
The master table of all merged, de-duplicated venues.
needs_enrichment
The "waiting room" — venues missing required data (address, coords) that can't go live yet.
cities tab
The list of charted cities, each with a centroid lat/lng.
Enrichment
Filling in a venue's missing data (mainly address + coordinates, later a photo).
Places Enrichment
A Sheet tab keyed by normalizedKey that maps venue names to Google Places data (placeId, lat/lng, address). This is what reshape consults to attach geo to award rows — the lookup is name-only, no city.
normKey_
The normalization function inside reshape.gs that turns a venue name into a lookup key. Four character-class fixes are verified to live here (see §6); the rule is one regex per patch, verified against Places Enrichment first.
Chain collision
Fixed June 5, 2026. Reshape once identified venues by name only, so same-named venues in different cities (L'Atelier de Joël Robuchon; Atlas Atlanta/Singapore) collapsed into one record and shared awards/type. Identity is now normKey + cityKey, which separates them. See §7 and §6.
cityKey_
Companion to normKey_ added June 5, 2026. Normalizes a city label (accents, apostrophes, punctuation) plus a few hard equivalences (New York City → new york, Washington DC → washington) so it can join the name to form venue identity. The eventual city-label canonicalization map will live here.
collision_audit / geo_audit / dupe_audit
Read-only diagnostic tabs written by audit scripts. collision_audit lists names appearing in 2+ cities (collision risk); geo_audit lists rows sharing a placeId across cities; dupe_audit lists same name+city appearing as 2+ rows. Worklists for the open geo / canonicalization follow-ons.
closed_venues tab
A two-column tab (name, city) listing permanently closed venues. Reshape excludes anything matching from both venues and needs_enrichment. Reversible — clear the tab and they come back.
enrichment_audit tab
Output of enrichment-audit.gs: every row in needs_enrichment ranked by award prestige, color-coded by reshape's reason. The triage worklist.
Outlier detection
A passive pass that flags suspicious venue data (wrong-country coords, off ranks) for correction.
Source of truth
The Google Sheet — the one place data is edited. The site only reads from it.

Technical terms

Repo (repository)
The GitHub project holding the website's code: github.com/benjamineades/compasseats.
Static data
Pre-generated data files built ahead of time (fast, crawlable) — vs. data made on the fly.
Ephemeral
Temporary, not saved. Describes the old AI-generated-venue approach we're leaving.
AI-generated venues
The deprecated method where an LLM invented venues at request time. Being replaced by static Sheet data.
Slug
A URL-safe version of a name (e.g. new-york for "New York").
Permalink
A permanent, stable URL for a page (so it can be linked and indexed by Google).
Geocoding
Converting an address or place name into latitude/longitude coordinates.
Centroid
The average center point of all a city's venues — used to center its map.
Apps Script
Google's built-in JavaScript automation that runs inside Google Sheets.
.gs
The file extension for an Apps Script file.
Zod
A JavaScript library for validating that data matches a defined shape (used in schema.ts).
Schema
The defined structure/shape data must conform to.
AWARD_SOURCES registry
The list in schema.ts that tells the site about each award source (name, slug, styling/weight). 18 currently.
JSON-LD / Schema.org
A structured-data format embedded in pages so search engines understand them (SEO).
venues-index.json
The slim search index loaded by the browser for fast city/venue search.
Lovable
The AI-assisted frontend builder Ben uses to make changes.
Lovable prompt
A change instruction written specifically for Lovable to execute.
TanStack Start
The React framework powering the site.
Tailwind v4
The CSS framework used for styling.
oklch
A perceptually-uniform color format used for the design tokens.
Bun
The JavaScript runtime and package manager used.
Cloudflare
The hosting/deployment platform.
MapLibre GL JS
The open-source map renderer (replaced Google Maps).
MapTiler
The provider of the map tiles / basemap.
Geoapify
The free geocoder used as a fallback for searching any uncharted city.
Nominatim
OpenStreetMap's free geocoder (an alternative option).
Basemap
The underlying map layer (streets, terrain) the pins sit on.
Clustering
Grouping nearby map pins into one marker when zoomed out.
Popover
The info card that appears when you click a map pin.
CDN
Content Delivery Network — for serving/caching images quickly and cheaply.
Design token
A named design value (color, font), e.g. --primary.
Brass / Bronze
The gold accent colors — brass #C6A15B for fills, bronze #895F2E for text on light.
Canonical URL
The official/preferred URL for a page, declared for SEO.
OG image (Open Graph)
The preview image shown when a link is shared on social/messaging.

Award shorthand

W50
World's 50 Best (Restaurants or Bars).
OAD
Opinionated About Dining (a restaurant ranking).
50 Best Bars
The World's 50 Best Bars.
Spirited Awards
Tales of the Cocktail's bar/bartender awards.
