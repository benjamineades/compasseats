01 — The Pattern

One architecture, two implementations.

CompassEats has a single ingest pattern, implemented twice — once for bars (live today) and once for restaurants (mirroring it, coming next). Same shape, different inputs.

02 — The Bar Ingest Tool

compasseats-bar-ingest.gs

The live, working ingest tool. Built to absorb published bar lists (50 Best Bars and its regional spin-offs, Spirited Awards lists, etc.) without you having to hand-reformat anything.

The two functions

makeBarImportTemplate Run first
Creates a fresh import-template tab in the Sheet with the columns the ingestion expects. Run this once per list you want to bring in. You then paste your list into that tab.
ingestBarLists Run second
Reads the filled-in template, de-dupes each entry against the Bar Awards tab (by source_slug + year + normalized name), and appends new award rows to Bar Awards. It does not write to venues — reshape reads Bar Awards as a source and folds it in. This is what lets ingested bars survive every reshape.

What "ingest" does

When ingest runs, every pasted row is turned into one award row and written to the Bar Awards tab (restaurants → Restaurant Awards). Two outcomes per row:

  • Added — a new award row is appended to Bar Awards. On the next reshape, it's matched to geo and either lands in venues (if found in Places Enrichment) or in needs_enrichment (if not).
  • Skipped (duplicate) — an identical source_slug + year + name already exists in Bar Awards (the restaurant tool's dedupe was updated June 12, 2026 to key on source_slug + year + name + city, so same-name venues in different cities — e.g. Sushi Sho NY vs Stockholm — are no longer collapsed), so the row is ignored. This is how the same bar across multiple years correctly stacks distinct awards without duplicating.

The actual append-to-existing-venue and route-to-needs_enrichment decisions now happen in reshape, not ingest — because reshape is the single place that merges all award sources and matches them to Places Enrichment. Ingest's only job is to get clean award rows into the awards tab.

★ Why this matters

Keeping a venue's award history un-fragmented now happens in reshape, which groups every award row by venue identity. If Connaught Bar appears in Bar Awards under several years, reshape collects them all onto one venue record — a stacked accolade history, not duplicate rows. Ingest's per-row dedupe just prevents the same award (same slug + year) being listed twice.

🌏 Non-Latin names & country codes (June 1)

Reshape's slugify_ now handles venues with non-Latin names (Chinese, Japanese, Korean, Thai). Previously these slugified to an empty string and the deduper produced broken slugs like -2, -3; now an empty result falls back to {city-slug}-{placeId tail} (e.g. tokyo-ireai) — always valid, unique, and stable across re-syncs. Existing Latin slugs are unchanged.

Separately, the cities generator (generateCitiesTab) maps each country name to an ISO-3166 alpha-2 country_code via a lookup table that was expanded to cover ~40 more countries. Any country still missing a code shows blank and fails the build's validation gate — fix it by adding the country to the table, or type the 2-letter code directly into the country_code cell (manual edits are preserved on re-run). A blank country field upstream needs fixing at the source award tab.

03 — Step-by-Step

Ingesting a bar list, start to finish.

Twelve steps from a published list to charted venues on the website.

  1. Have your source list ready — the rankings page, an export, or any clean copy/paste source.
  2. In the Sheet, click Extensions → Apps Script. The editor opens in a new tab.
  3. In the left sidebar, click compasseats-bar-ingest.gs.
  4. From the function dropdown at the top, select makeBarImportTemplate, then click ▶ Run. Authorize on first run.
  5. Switch back to the Sheet. You'll see a new import-template tab ready for your list. Read its column headers — that's the shape ingest expects.
  6. Paste your list into the template, matching the column shape (typically rank, venue name, city, country, and the source/year metadata).
  7. Sanity-check the pasted rows: cities spelled consistently, ranks numeric, source name correct.
  8. Back in Apps Script, select ingestBarLists from the dropdown and click ▶ Run.
  9. Read the Execution log. It reports award rows added to Bar Awards, plus duplicates / invalid / blank rows skipped.
  10. Run reshape from compasseats-reshape.gs to fold the Bar Awards rows into venues (matched to geo) and route geo-less ones to needs_enrichment.
  11. Enrich any rows that landed in needs_enrichment — fill addresses and lat/lng (see Handbook §7).
  12. Run reshape a second time to promote newly-enriched rows into venues. Sync & deploy.
🧭 Reading the log

Ingest's log tells you how many award rows it added to Bar Awards and how many it skipped (duplicates, invalid slugs, blanks). The appended vs new vs needs_enrichment split now appears in reshape's log instead — that's the step that matches each award row to geo. A reshape where "of which bars" climbs is your confirmation the bars went live.

04 — A Worked Example

The first N. America 51–100 paste.

Here's how the tool actually behaved on a real ingestion — a useful benchmark for what to expect.

Real run
North America's 50 Best Bars 51–100 — first paste
40
Appended
8
New venues
52
→ needs_enrichment

Out of ~100 entries, 40 already existed in venues and gained a new accolade. 8 were brand-new venues that came in clean. 52 landed in needs_enrichment because they were recognized as new but were missing addresses or coordinates — the most common ingestion outcome for any list with venues we haven't catalogued before.

What that tells you

  • The high appended count is a healthy sign of cross-list overlap — many top bars appear on multiple guides, and the tool is correctly recognizing them as the same venue, not creating duplicates.
  • The 52 in needs_enrichment is the next-step queue, not an error. Each one needs an address + lat/lng to graduate to venues.
  • If you ever see a run where new is suspiciously high — say, 80 out of 100 — that's a flag that matching is failing (city spellings off, name variants not normalizing). Worth pausing and checking before reshape.

⚙️ Mixing lists is now fine

The v2 tools read every row independently by its own source_slug, year, and rank — so you can pile multiple years, ranking bands, and even regions into one import tab and ingest them in a single run. Example: North America 1–50 (2026), 1–50 (2025), and 51–100 (2026) can all sit in one tab together. The only discipline is per-row accuracy: each row's slug must match its rank band (1–50 rows use the base slug; 51–100 rows use the -51-100 slug), the year must be right, and names clean. Dedupe is by slug + year + name, so the same venue across different years correctly stacks as separate awards.

06 — The Restaurant Ingest Tool

Built — and live alongside the bar tool.

The restaurant tool follows the bar tool's pattern exactly — same two-function workflow, same name-matching, same awards_json dedupe, same routing to needs_enrichment, same 23-column venues rows — tuned for restaurant lists with two extra optional venue-attribute columns and a flexible grading field.

📦 Source data already compiled

All four current regional restaurant lists are compiled into staged import files: Asia's 50 Best Restaurants (2019, 2021–26, full 1–100 where published), Latin America's 50 Best Restaurants (2019, 2020, 2022–25), North America's 50 Best Restaurants (2025–26), and MENA's 50 Best Restaurants (2022–26). Missing originals recovered via the web: Asia 2021 (1–100) and the MENA 2022 No.1 (3 Fils). One row carries a deliberately blank country — MENA 2024 #25 Nomi, whose published city "Monash" isn't a MENA location — flagged for manual verification. La Liste 2026 is also on hand (a score-based list, reshaped on ingest — see below).

✱ Two important design decisions (June 2)

Grading lives in category_override, never in its own column. Awards grade venues differently — a numeric rank (No. 1), Michelin stars (Two Stars), Best Chef knives (3 Knives), La Liste scores (99.5/100), Gault & Millau toques. Rather than a column per system, a plain numeric rank goes in rank (auto-labels "No. {rank}") and any other grading goes in category_override as free text. A brand-new award type needs no script change and no new column.

One slug per region. Unlike the bars (which use split …-51-100 slugs), each restaurant region is a single source covering the full 1–100. Cleaner, and there's no legacy restaurant data to migrate.

The two functions

compasseats-restaurant-ingest.gs Live
The script file. Sits alongside the bar tool in Apps Script.
makeRestaurantImportTemplate Live
Creates the import tab with columns source_slug, year, rank, name, city, country, category_override, cuisine, price_band. The first six match the bar shape; the last three are optional.
ingestRestaurantLists Live
Mirror of ingestBarLists. De-dupes by source_slug + year + normalized name and appends new rows to the Restaurant Awards tab (carrying cuisine and price_band through). Does not write to venues — reshape reads Restaurant Awards and folds it in.
🔤 Accepts display names or slugs

The compiled files carry the full award name in the source column (e.g. Asia's 50 Best Restaurants), not the slug. The tool's resolveSourceR_ step translates known display names to their registry slug automatically — handling smart apostrophes, & vs "and", and spacing — so the files paste in as-is. A row already in slug form passes straight through. Unknown sources are counted as invalid and skipped (visible in the log).

Where the optional fields land

  • cuisine → venues.cuisine_tags (backfilled only if empty — never clobbers existing data).
  • price_band → venues.price_tier (same backfill-only rule).
  • Both can be blank, so the 6-column compiled files work without edits.

La Liste — the score-based exception

La Liste's source file is shaped differently (Score, Name, City, State, Country — no source/year/rank). It's reshaped into the template on ingest: Score → category_override as {score}/100 (e.g. 99.5/100), source = la-liste, year from the file title, rank left blank, State ignored (city + country drive matching).

⚠️ Registry first, or the build breaks

Five regional restaurant slugs (asia-50-best-restaurants, latin-america-50-best-restaurants, north-america-50-best-restaurants, mena-50-best-restaurants, africa-50-best-restaurants) must be added to AWARD_SOURCES in schema.ts before reshape/deploy. The schema's validation gate rejects any venue carrying an unregistered award source. Ingesting into the Sheet is safe either way — the gate only bites on rebuild.

◆ Why mirror, not unify

Restaurants and bars share a lot, but not everything. Restaurants carry cuisine and price band; bars have signature drinks and bartender awards. Keeping the two tools as separate mirrors (rather than one unified ingest) lets each evolve its own quirks without contaminating the other. Same architecture, room to specialize.

07 — Adding Award Sources

Both tools must make this easy.

A hard requirement of the ingest tools: adding a new award source (a new guide, a new regional list) should never require rewriting script code. New source → one paste, one config entry, done.

The two-place rule

A new award source touches exactly two places in the system. Get both right and it works end-to-end. (This rule comes from Handbook §5 — repeated here in the ingest context.)

Layer 1 · The Sheet

Run the ingest tool's template function, paste the list. The tool routes everything into venues and needs_enrichment — no script edit needed as long as the list matches the template shape.

Layer 2 · The Code

Add an entry to the AWARD_SOURCES registry in src/lib/schema.ts so the website knows how to label, weight, and link the new source. Without this, the data exists but won't render nicely.

⚙️ Without Layer 2

If you ingest a list whose source isn't in AWARD_SOURCES yet, the venues will still appear on the site — but the accolade will show as a raw source key (something like tabelog_2024) instead of a clean label. Always pair an ingest with a registry update.

08 — Troubleshooting

When something looks off.

"Too many new venues" in the log

If a list of 100 entries yields 80+ new with very few appended, the matcher is probably failing. Common causes:

  • City spelling mismatch — your pasted list says "New York City"; venues has "New York". Normalize to one form.
  • Name variants — "The Connaught Bar" vs "Connaught Bar". A leading article can break the match.
  • Encoding artifacts — smart quotes, em-dashes, dual-script names. Clean these in the template before ingest.

Cancel the ingest, fix the template, and re-run.

Everything went to needs_enrichment

If routed is 90%+, the template shape is probably wrong — the tool is recognizing the source but can't read the rest of the columns. Re-check that you pasted into the right columns and that the source/year metadata is filled in correctly.

The Execution log is empty or vague

Apps Script sometimes buffers logs. Hit View → Logs manually. If the log still looks empty, check the Sheet — the changes will be there even if the log didn't surface them.

A venue ended up duplicated

This is the rarest case but worth knowing. If the matcher missed an obvious match (different spelling slipped through), you'll end up with two rows for the same venue. Fix it manually in venues by merging the accolades onto the canonical row and deleting the duplicate. Then add the alternate spelling to your normalization list so it doesn't happen again.

🧠 Trust but verify

After every ingest, the highest-leverage 30 seconds you can spend is opening venues, sorting by date added (or by source), and eyeballing the top 20 new entries. You'll catch most of the above issues at a glance.
