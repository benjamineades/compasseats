Re-Architecture & Migration Plan

Version 1.19 Updated September 14, 2026 Author Claude Fable 5 Status Michelin 2026 under way · France promoted · Italy next Responds to michelin-2026-france promoted Sep 14 · PR #4 (stage speed + loose-name pass)

A phased plan to rebuild CompassEats, and later Compass Local, on a licence-compliant, automated foundation that one non-technical operator runs alone. It is a design, not code. Every phase names its model and surface, the decisions that need Ben's judgment, effort in Ben's hours, and its rollback position. The decision register in §1 is the work to finish before August 18.

The shape of the change, in one look

Today: Google Sheet (truth) → Apps Script (9-step manual order) → JSON → GitHub drag-drop → Lovable → Lovable's Cloudflare account → compasseats.com
After: Postgres (truth, constrained) → jobs in GitHub Actions (staging → report → Ben approves → promote) → versioned, sharded JSON artifacts → Ben's Cloudflare account → compasseats.com
            Google Sheets survive only as disposable review surfaces. Nothing Google-derived is stored except placeId for the photo Worker.

Four structural moves carry the whole design. One: venue identity moves from names and slugs to immutable internal IDs, which kills the collision class and the orphaned-content class permanently. Two: every data mutation becomes a staged job that produces a diff report and cannot promote without Ben's explicit approval — the silent-failure class dies because nothing writes in place. Three: the publish is a versioned artifact with a one-click "promote previous version" rollback, so a bad publish is a two-minute problem, not a forensic one. Four: every field knows which publisher it came from, so exposure per publisher is a live number with a cap, any publisher's data can be switched off cleanly on request, and no single guide is ever a structural dependency — the architecture's answer to a legal question it cannot itself resolve.

02Where this plan pushes back on the brief

1 · The three-month clock is realistic for foundation plus swap, with one honest caveat. The long pole after August 18 is not build time — Claude Code and Cowork carry that — it is Ben's design-review time, which lives in weekend hours. The plan protects the clock two ways: D7 halves the taste decisions, and Phase 4 reviews are batched into three structured weekend sessions rather than a drip. If reviews slip, the swap date slips; scope does not.

2 · The diversification theory needs one stress test before the plan leans on it. The brief's reading — insubstantial extraction from each of several databases breaches none of them — is the standard one. But the same directive also prohibits repeated and systematic extraction of insubstantial parts where it cumulates toward a substantial one (Article 7(5); the BHB ruling read this as cumulation toward reconstitution). Ten years of ingest could cumulate against one publisher even while every snapshot looks diversified. That is why D10's ledger is cumulative over all time, not a current ratio. Whether diversification holds as the primary mitigation is a question for the specialist, not a conclusion from here — the design costs nothing either way. (v1.0's flag on small-batch capture is retired: the assumption was withdrawn and the specialist is being retained, which is the right response.)

3 · Permission-then-capture, never capture-then-ask. With a Michelin conversation opening, sequencing is strategy. Per-publisher guide capture stays off until that publisher's permission or the specialist's clearance arrives, whichever comes first. Capturing first would poison the exact negotiation the brief correctly calls the clean exit — and the non-commercial, full-credit, traffic-back posture is only worth its negotiating weight if the conduct matches it on the day the conversation starts.

4 · The brief says the Sheet is replaceable. This plan replaces it as truth but deliberately keeps spreadsheets in the loop as review surfaces. Reviewing a queue of rows is Ben's fastest, most reliable motion. A pure database review UI would be slower for him and more to build. The line that matters: a spreadsheet may hold a copy for review; it may never again be the record.

5 · One survivor list correction. "What survives" should explicitly include the slug → venue mapping for every currently indexed URL. It is implied by "existing URLs unchanged," but it is a migration input that must be extracted and verified, not an emergent property. Phase 1 treats it as first-class data.

6 · Days-open stays in the model, unblocked and unblocking. The venue schema carries days_open with provenance and a confidence flag from day one, populated opportunistically at ingest. Nothing waits on it, and Tonight mode's honest version ("open days confirmed / hours not tracked — call ahead") has a home when its pilot starts.

03Target architecture

Where the data lives, and how Ben edits it

Canonical store: Supabase (managed Postgres), Pro plan, $25/month. Chosen over alternatives for four properties that map directly onto this project's scar tissue: real constraints (a write that would orphan or collapse data fails loudly instead of succeeding quietly), real transactions (a timed-out job leaves zero rows changed, never 9,166 of 11,774), daily backups included, and a built-in spreadsheet-style Table Editor.

Ben's editing interface, concretely. For a point fix — a typo, a closed venue, a wrong city — the path is: supabase.com → project → Table Editor → pick the table → filter by name → click the cell → type → save. It looks and feels like a locked-down spreadsheet. For anything touching more than a handful of rows, Ben never edits by hand: he asks Claude, Claude prepares the job, the job produces a report, Ben approves. That split — hand edits for ones, jobs for many — is itself a guard.

Review surfaces. When a batch needs human eyes (geo review queue, merge candidates, ingest anomalies), the job exports a CSV, Ben reviews it in Google Sheets exactly as today, marks accept/reject, and the decisions import back. The Sheet copy is disposable; the record never leaves Postgres.

Why not the alternatives. Keeping the Sheet canonical keeps the disease (no constraints, silent partial writes) under new plumbing. Airtable adds a friendlier UI but weaker guarantees and a new proprietary dependency. Cloudflare D1 is native to the stack but pairs a thinner admin UI with a weaker backup story — the wrong trade for a solo non-technical operator.

The pipeline: jobs, reports, approvals

Every transformation the Apps Script suite does today becomes a script in the repo, run by GitHub Actions. Ben's interface is the Actions tab → pick a workflow → "Run workflow" button. Three properties are non-negotiable in every job:

  • Staging first. Jobs write to staging tables, never live ones. A promote step moves staged data live inside a single transaction.
  • Report before promote. Every run emits a plain-language report: rows in, rows out, counts by table before/after, invariant results, and a sample of changes. Promotion requires Ben to run the promote workflow and type PUBLISH into a confirmation field. Nothing promotes on its own.
  • Idempotent by batch ID. Re-running a job with the same batch ID is a no-op, which retires the "report timed out so I ran it twice and duplicated the work" class.

The nine-step manual run order collapses to: run ingest or fix job → read report → approve → run publish → read diff → approve. Order-dependence is enforced in code, not memory.

The publish: versioned, sharded, app-ready

The site stays static — that model is cheap, fast, and right. Two changes future-proof it:

  • Sharded artifacts. One index.json plus per-city venue files replace the 11 MB monolith. This clears the 25 MB Worker-bundle ceiling well past 15,000 venues, speeds builds, and — because a mobile app can read the exact same files — is the "mobile-app-ready" answer without running a server. If the app later needs live queries, Supabase's API is already sitting under everything.
  • Versioned with one-click rollback. Each publish writes to a dated version folder plus a manifest pointer. Rollback is a workflow called promote-previous-version: one click, live in about two minutes, no forensics required first.

Frontend and hosting

Same stack — TanStack Start, React 19, Tailwind v4, MapLibre/MapTiler — deployed from GitHub to Ben's own Cloudflare account. Every change is a pull request with a preview URL; Ben reviews the preview on his phone or laptop and clicks merge. Production deploys only from approved merges. The frontend is rebuilt (layout and UX restarted, brand evolved per D7) against the new artifacts by Claude Code, with the existing Lovable-hosted site serving traffic untouched until the swap in Phase 5.

Non-commercial by construction. No ad slots, no sponsored-placement fields in the data model, no affiliate parameters anywhere in the codebase — when reservation deep links arrive on the roadmap, they ship as plain URLs, and the brief's specific trap (booking-platform commission) is named in the frontend's contribution notes so no future session reintroduces it. A Sources & credits page, generated from award_sources, names and links every guide — the traffic-back posture made visible. The published JSON artifacts exist to serve the site, not as a dataset offering: no export or download surface, ever.
